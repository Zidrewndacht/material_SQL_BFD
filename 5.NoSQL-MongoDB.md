# Bancos Não-Relacionais (MongoDB) e Concorrência

**Pré-requisitos:** SQLite (e seus limites), Dicionários e Listas em Python, JSON, Flask básico.
**Ambiente:** MongoDB (via Docker ou Atlas), Python com drivers `pymongo` e `motor`.
**Objetivo:** Entender o paradigma NoSQL, resolver o gargalo de concorrência do SQLite e aplicar MongoDB em APIs Web.

---

## 0. O Limite do SQLite e a "Impedância"

Nas aulas anteriores, o **SQLite** se provou uma ferramenta excepcional. Ele é rápido, não exige instalação e é perfeito para aplicações web com tráfego moderado. Porém, como vimos, ele possui duas limitações arquiteturais importantes à medida que o sistema cresce:

1.  **O Problema da Concorrência (`database is locked`):** O SQLite é um *arquivo único no disco*. Se você tiver um Web Scraper ou um Worker de fundo *escrevendo* dados no banco constantemente, e um usuário acessar a API Flask para *ler* esses dados ao mesmo tempo, o SQLite travará o arquivo e retornará `sqlite3.OperationalError: database is locked`.
2.  **A "Impedance Mismatch" (Incompatibilidade de Impedância):** A web moderna trafega **JSON**. O frontend (JavaScript) consome **JSON**. O Python trabalha com **Dicionários**. No SQL, você é obrigado a "desmontar" seu dicionário em colunas planas para salvar, e "remontar" (fazer `JOINs` e loops) para ler. Essa tradução constante gera fricção.

Para cenários de **alta taxa de escrita**, dados hierárquicos ou flexíveis, precisamos de um banco de dados que opere como um **serviço independente** (Cliente-Servidor) e que fale a mesma língua da Web. É aqui que entra o **MongoDB**.

---

## 1. O Paradigma de Documentos (BSON)

**NoSQL** (*Not Only SQL*) abandona as tabelas rígidas. O **MongoDB** é um banco **orientado a documentos**. Em vez de tabelas e linhas, usamos **Coleções** e **Documentos BSON** (Binary JSON).

Na prática, isso significa que **você insere dicionários Python e listas nativas diretamente no banco**. O banco não rejeitará uma inserção só porque falta uma "coluna" (Schema Dinâmico).

| Conceito Relacional (SQLite) | Conceito MongoDB | Python Equivalente |
| :--- | :--- | :--- |
| Tabela (*Table*) | Coleção (*Collection*) | - |
| Linha (*Row*) | Documento (*Document*) | `dict` |
| Coluna (*Column*) | Campo (*Field*) | Chave do `dict` |
| `JOIN` / Tabela Associativa | `Embedding` (Aninhamento) | `list` ou `dict` aninhado |

### O Fim das Tabelas Associativas para Arrays
Imagine um catálogo de e-commerce. Uma Smart TV tem `polegadas`, uma Camiseta tem `tamanho`.
*   **No SQLite:** Teríamos que criar colunas que seriam `NULL` para metade dos produtos, ou usar JSONB.
*   **No MongoDB:** Armazenamos exatamente como o Python e o JavaScript gostam.

```python
# Documento 1 (Eletrônico)
{"nome": "Smart TV 4K", "preco": 2500.0, "atributos": {"polegadas": 55, "hdr": True}}

# Documento 2 (Vestuário)
{"nome": "Camiseta Python", "preco": 49.90, "atributos": {"tamanho": "G", "cor": "preto"}}
```

## 2. Exemplo Guiado Mínimo: O Catálogo Flexível

Para rodar este exemplo, você precisa de um MongoDB rodando. A forma mais rápida em 2026 é via Docker:
`docker run -d -p 27017:27017 --name meu-mongo mongo:latest`

Abaixo, um script **completo e executável** usando o driver síncrono oficial, o **`pymongo`** (`pip install pymongo`).

```python
from pymongo import MongoClient
from datetime import datetime

# 1. Conexão (Aponta para o container Docker local)
client = MongoClient("mongodb://localhost:27017/")
db = client["loja_db"]
produtos = db["produtos"]

# Limpa a coleção para testes repetidos
produtos.delete_many({})

# 2. Inserção de Documentos (DML)
# Note que usamos dicionários Python nativos. O pymongo converte para BSON.
catalogo = [
    {
        "nome": "Smart TV 4K",
        "categoria": "Eletrônicos",
        "preco": 2500.00,
        "estoque": 10,
        "atributos": {"polegadas": 55, "hdr": True},
        "tags": ["promoção", "sala"]
    },
    {
        "nome": "Camiseta Python",
        "categoria": "Vestuário",
        "preco": 49.90,
        "estoque": 50,
        "atributos": {"tamanho": "G", "cor": "preto", "material": "algodão"},
        "tags": ["vestuário", "programação"]
    }
]

resultado = produtos.insert_many(catalogo)
print(f"IDs gerados automaticamente: {resultado.inserted_ids}")

# 3. Consultas (DQL) e Filtros Aninhados
# Como buscar apenas produtos que sejam "pretos"?
# Usamos a notação de ponto (dot notation) para atravessar o dicionário aninhado.
print("\n--- Buscando produtos pretos ---")
cursor = produtos.find({"atributos.cor": "preto"})
for doc in cursor:
    print(f"Achado: {doc['nome']} - Tamanho: {doc['atributos']['tamanho']}")

# 4. Atualização (Update) com Operadores
# No SQL: UPDATE produtos SET estoque = estoque - 1 WHERE nome = 'Smart TV 4K'
# No Mongo: Usamos operadores de atualização como $set, $inc, $push
produtos.update_one(
    {"nome": "Smart TV 4K"},
    {
        "$inc": {"estoque": -1},          # Decrementa o estoque
        "$push": {"tags": "blackfriday"}  # Adiciona um item ao array 'tags'
    }
)

# 5. Verificando a atualização
tv_atualizada = produtos.find_one({"nome": "Smart TV 4K"})
print(f"\nEstoque atual da TV: {tv_atualizada['estoque']}")
print(f"Tags da TV: {tv_atualizada['tags']}")
```

### O Identificador `_id` e o `ObjectId`
Note que não definimos um `id` nos nossos dicionários. O MongoDB gera automaticamente um campo chamado `_id` do tipo `ObjectId`.
*   O `ObjectId` é um identificador de 12 bytes que contém a **data de criação** embutida.
*   **Vantagem:** Você pode ordenar documentos por data de inserção apenas ordenando pelo `_id`, sem precisar de uma coluna `created_at`.

## 3. A Dualidade dos Drivers: Síncrono (`pymongo`) vs Assíncrono (`pymongo.AsyncMongoClient`)

O Python moderno possui dois mundos: o síncrono tradicional e o assíncrono (`asyncio`). Por muitos anos, o ecossistema MongoDB ofereceu dois drivers separados para atender a essas necessidades: o **`pymongo`** (síncrono) e o **`motor`** (assíncrono). No entanto, essa realidade mudou.

### O Fim do `motor` e a Unificação no `pymongo`

Em **14 de maio de 2025**, o driver `motor` foi oficialmente **depreciado** em favor da API assíncrona nativa do próprio `pymongo`, que atingiu o status de *General Availability* (GA) na versão **4.13.0**. O `motor` não receberá mais novos recursos e só continuará recebendo correções de bugs até **14 de maio de 2026** (fim da vida útil), com suporte a correções críticas se estendendo até **14 de maio de 2027**.

> **Nota para 2026:** É muito provável que você encontre `motor` em projetos legados, tutoriais antigos ou documentações desatualizadas. A MongoDB recomenda fortemente a migração para a API assíncrona do `pymongo`.

A boa notícia é que a migração é **extremamente simples**: em quase todos os casos, basta substituir `AsyncIOMotorClient` por `AsyncMongoClient` e ajustar as importações de `motor.motor_asyncio` para `pymongo`.

### Tabela Comparativa Atualizada (2026)

| Driver | Paradigma | Status em 2026 | Caso de Uso Ideal |
| :--- | :--- | :--- | :--- |
| **`pymongo`** (`MongoClient`) | Síncrono (Bloqueante) | **Ativo e recomendado** | **Backends Web tradicionais (Flask, Django)**, scripts de migração, ETLs. |
| **`pymongo`** (`AsyncMongoClient`) | Assíncrono (`asyncio`) | **Ativo e recomendado (GA desde 2025)** | **Workers de fundo**, IoT, WebSockets, Scrapers, coleta de dados em alta frequência. |
| **`motor`** (`AsyncIOMotorClient`) | Assíncrono (`asyncio`) | **Depreciado** (EOL: Maio/2026) | Apenas para manutenção de projetos legados. **Não use em novos projetos.** |

### Exemplo Prático: Inserção Assíncrona com `AsyncMongoClient`

O driver `pymongo` agora oferece uma API assíncrona completa, incluindo o `AsyncMongoClient`, que gerencia um pool de conexões e é seguro para uso em contextos concorrentes. Veja um exemplo executável:

```python
import asyncio
from pymongo import AsyncMongoClient

async def main():
    # Conexão usando o novo cliente assíncrono
    async with AsyncMongoClient("mongodb://localhost:27017/") as client:
        db = client["loja_db"]
        produtos = db["produtos"]

        # Limpa a coleção para testes
        await produtos.delete_many({})

        # Inserção assíncrona
        catalogo = [
            {
                "nome": "Smart TV 4K",
                "categoria": "Eletrônicos",
                "preco": 2500.00,
                "atributos": {"polegadas": 55, "hdr": True}
            },
            {
                "nome": "Camiseta Python",
                "categoria": "Vestuário",
                "preco": 49.90,
                "atributos": {"tamanho": "G", "cor": "preto"}
            }
        ]
        resultado = await produtos.insert_many(catalogo)
        print(f"IDs inseridos: {[str(id) for id in resultado.inserted_ids]}")

        # Consulta assíncrona
        async for doc in produtos.find({"atributos.cor": "preto"}):
            print(f"Achado: {doc['nome']}")

        # Atualização assíncrona
        await produtos.update_one(
            {"nome": "Smart TV 4K"},
            {"$inc": {"estoque": -1}, "$push": {"tags": "blackfriday"}}
        )

asyncio.run(main())
```

**Principais diferenças em relação ao código síncrono:**
1.  **`async with`**: O `AsyncMongoClient` deve ser usado como um gerenciador de contexto assíncrono para garantir que o pool de conexões seja fechado corretamente.
2.  **`await`**: Todas as operações de I/O (inserção, consulta, atualização) são precedidas por `await`.
3.  **`async for`**: A iteração sobre cursores de consulta também é assíncrona.
4.  **Contexto de Execução**: Este código deve ser executado dentro de um *event loop* (ex: `asyncio.run()`), não em uma rota síncrona do Flask.

### Boas Práticas para o Novo Driver Assíncrono

1.  **Reutilize o Cliente**: Assim como no `pymongo` síncrono, crie **uma única instância** do `AsyncMongoClient` por processo/aplicação e a reutilize em todas as operações. O cliente gerencia internamente um pool de conexões; criar um novo cliente a cada requisição esgotará os limites de conexão.
2.  **Configure o Pool**: Para serviços de alta concorrência, ajuste o tamanho do pool no cliente ou na string de conexão (ex: `maxPoolSize=200`) para atender à demanda.
3.  **Use em FastAPI/Workers**: A API assíncrona brilha em frameworks modernos como FastAPI, em workers de coleta de dados e em qualquer contexto onde a concorrência de I/O seja um gargalo. Para rotas Flask síncronas, continue usando o `pymongo` tradicional.

### Resumo da Seção

- O `motor` foi depreciado e não deve ser usado em novos projetos. Seu fim de vida está marcado para **14 de maio de 2026**.
- A API assíncrona nativa do `pymongo` (`AsyncMongoClient`) é o **novo padrão** para operações assíncronas com MongoDB.
- A migração do `motor` para o `AsyncMongoClient` é simples: troque a classe do cliente e as importações.
- Escolha o driver certo para a camada certa: `MongoClient` para Flask/Django síncronos, `AsyncMongoClient` para workers `asyncio`, FastAPI, IoT e coleta de dados em alta frequência.

## 4. Estudo de Caso Real: nPEE Microgrid (Induscon 2025)

Para entender como o MongoDB é usado na indústria para resolver o problema do `database is locked` do SQLite, vamos analisar a arquitetura do projeto open-source **[nPEE Microgrid](https://github.com/Zidrewndacht/npee-microgrid)**, apresentado no *Induscon 2025*.

O sistema monitora uma microrrede elétrica (painéis solares, baterias, medidores) em tempo real. A arquitetura é orquestrada via **Docker Compose** e dividida em três atores:

```text
[ Sensores / Simulador Modbus ]
          │ (TCP/IP)
          ▼
[ Coletor IoT (Python + asyncio + MOTOR) ] ──► (ESCREVE em alta frequência) ──┐
                                                                              │
                                                                         [ MongoDB ]
                                                                              │
[ Frontend JS (Chart.js) ] ◄── [ Backend Web (Flask + PYMONGO) ] ◄── (LÊ / API REST)
```

### Por que MongoDB e não SQLite aqui?
1.  **Concorrência Extrema:** O Coletor lê sensores e *escreve* no banco a cada 100ms. Vários usuários *leem* os gráficos via Flask simultaneamente. O SQLite provavelmente colapsaria com `database is locked`. O MongoDB, rodando como serviço, gerencia isso nativamente.
2.  **Arrays Nativos para Séries Temporais:** O medidor lê **Tensões Trifásicas** (Fase 1, Fase 2, Fase 3). No MongoDB, o Coletor insere isso como uma lista nativa: `{"tensao_por_fase": [127.5, 126.8, 128.1]}`. O Chart.js no frontend recebe esse array e desenha as 3 linhas do gráfico imediatamente, sem que o Flask precise fazer `JOINs` ou loops complexos.
3.  **Assincronismo no Worker:** O Coletor usa o driver **`motor`** (`motor.motor_asyncio`). Isso permite que o Python leia dezenas de sensores via rede e espere o MongoDB salvar sem bloquear a *thread* principal do coletor.

### A "Pegadinha" da Serialização JSON no Flask
O MongoDB armazena datas como objetos `datetime` do Python e IDs como `ObjectId`. O Flask **não sabe** transformar isso em JSON nativamente (dará `TypeError`).
No projeto nPEE, o backend Flask (usando **`pymongo`**) resolve isso com o módulo `bson.json_util`:

```python
# Trecho adaptado do backend Flask do nPEE
from bson import json_util
from flask import Response
from pymongo import MongoClient, DESCENDING

db = MongoClient("mongodb://mongodb:27017/")["modbus_data"]

@app.route('/api/data/<collection>/<int:limit>')
def get_data(collection, limit):
    # Busca os últimos N pontos, do mais recente para o mais antigo
    data = list(
        db[collection]
        .find()
        .sort('datetime', DESCENDING)
        .limit(limit)
    )
    
    # json_util.dumps converte ObjectId e datetime em formatos 
    # que o JavaScript (Chart.js) consegue ler nativamente.
    return Response(
        json_util.dumps(data),
        mimetype='application/json'
    )
```

## 5. Modelagem: Embedding vs Referencing

No modelo relacional (SQLite/PostgreSQL), a regra é a **Normalização**: evitar repetição de dados a todo custo.
No MongoDB, a regra é a **Desnormalização Orientada a Leitura**: *"Dados que são acessados juntos, devem ser armazenados juntos."*

*   **Embedding (Aninhamento):** Se um usuário tem múltiplos endereços, no MongoDB você geralmente guarda os endereços *dentro* do documento do usuário (como uma lista de dicionários). Uma única leitura (`find_one`) traz o usuário e todos os seus endereços. Zero `JOINs`.
*   **Referencing:** Se os dados crescem indefinidamente (ex: comentários de um post, logs de auditoria, telemetria de anos), você os separa em coleções diferentes e guarda o `ObjectId` como referência. Documentos no Mongo têm um limite rígido de **16 MB**.

## 6. Tabela Comparativa Definitiva: SQLite vs Postgres vs Mongo

| Cenário / Necessidade | SQLite | PostgreSQL | MongoDB |
| :--- | :--- | :--- | :--- |
| **Setup e Portabilidade** | Zero setup. Arquivo único. | Exige servidor e rede. | Exige servidor (geralmente Docker). |
| **Concorrência de Escrita** | Baixa (`database is locked`). | Altíssima (MVCC). | Altíssima (Otimizado para ingestão). |
| **Estrutura dos Dados** | Rígida (Tabelas/Colunas). | Rígida (mas suporta JSONB). | **Flexível (Schema Dinâmico / BSON).** |
| **Arrays e Listas** | Complexo (Tabelas 1:N). | Suporta `ARRAY` e JSONB. | **Nativo e Indexável.** |
| **Caso de Uso Típico** | Cache local, apps mobile, edge. | Sistemas Financeiros, ERP, SaaS. | **Catálogos, IoT, Logs, Perfis.** |
| **Driver Python (Web)** | `sqlite3` (Nativo) | `psycopg2` | `pymongo` |
| **Driver Python (Async)**| `aiosqlite` | `asyncpg` | `motor` |

## 7. Resumo e Boas Práticas

1.  **Não use MongoDB como um "PostgreSQL pior":** Se o seu problema exige integridade referencial estrita e `JOINs` complexos entre 5 tabelas (ex: sistema bancário), use um banco relacional. Use o Mongo para aproveitar a flexibilidade de documentos e alta taxa de ingestão.
2.  **Pense em como os dados serão lidos:** No SQL, modelamos para evitar duplicação. No MongoDB, modelamos baseados em *como o frontend consome o JSON*.
3.  **Índices são obrigatórios:** Consultar séries temporais sem índice em `datetime` destruirá a performance do seu banco em produção (o Mongo fará um *Collection Scan*, lendo tudo na memória).
4.  **Escolha o Driver Certo:** Use `pymongo` para rotas Flask/Django síncronas. Use `motor` para workers `asyncio` e coleta de dados.
5.  **Cuidado com a Serialização:** Lembre-se de usar `bson.json_util` ao devolver dados do Mongo para APIs JSON no Flask.
